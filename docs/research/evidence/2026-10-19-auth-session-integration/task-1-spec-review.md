# Task 1 independent specification review

Reviewed 2026-10-19 against `docs/superpowers/specs/2026-10-19-auth-session-integration.md` and Task 1 of its implementation plan. Comparison uses this batch's `baseline.json` and `before/`, not accumulated changes against HEAD. Implementation source was read independently before the implementation report.

## Findings

### P2 — Browser initialization still logs raw provider errors

- **Location:** `packages/web/src/lib/supabase.ts:42–44`.
- **Binding requirement:** specification clause 1, “client 创建不打印配置、凭据或原始 SDK 异常.”
- **Trigger:** an existing expired SDK cookie is present when `createClientSupabase()` creates the browser client, and refresh returns a provider error containing private diagnostic text. The facade supplies the default unsanitized browser transport. The installed SDK's initialization/recovery path logs the resulting `AuthApiError` internally.
- **Observed effect:** a reviewer-only probe using the actual facade and installed SDK, a synthetic expired cookie, and a mocked fetch response printed `AuthApiError: SYNTHETIC_PRIVATE_PROVIDER_SENTINEL`. There was one synthetic refresh request and no network. Removing the application's former `console.log` calls therefore does not satisfy the client-creation logging constraint.
- **Minimum fix:** sanitize browser Auth error bodies and thrown transport failures before the SDK receives them, preserving normal PKCE, cookie, refresh, and successful response behavior. Do not globally suppress console diagnostics. Add a regression for expired-cookie initialization with a raw provider sentinel and a thrown transport sentinel.
- **Evidence:** [probe source](spec-review-browser-init-probe.cjs), [actual probe output](spec-review-browser-init-probe.json). Command: `node .superpowers/sdd/2026-10-19-upgrade-auth-session-integration/spec-review-browser-init-probe.cjs`; exit 0, `rawSentinelLogged: true`.

### P2 — Concurrent valid token reads invalidate one another

- **Location:** `packages/web/src/stores/auth-store.ts:143–146` (also the return check at line 149).
- **Binding requirement:** clause 2 retains the public store actions and current valid session-token behavior, with generation invalidation for initialization, identity events, and explicit login/logout. A second read of the same unchanged valid session is not an identity invalidation.
- **Trigger:** two consumers call `getAccessToken()` concurrently after provider-confirmed initialization. Both reads increment the shared `generation`, so the first returns `null` solely because the second began.
- **Observed effect:** the actual store with a complete synthetic session returned `[null, "synthetic-access"]` while remaining authenticated as the same user. There was no signout, identity event, provider rejection, session loss, or network. Callers consequently omit an Authorization header despite a valid current session. For a concrete existing consumer, the purchase page builds its waitlist request from this result (`packages/web/src/app/[locale]/dashboard/purchase/page.tsx:57–62`), and the waitlist endpoint associates a user only from that header (`packages/web/src/app/api/waitlist/route.ts:29–45`); a concurrent read can make that operation anonymous. Cookie fallback in other endpoints does not repair the store API regression.
- **Minimum fix:** distinguish concurrent same-session reads from identity-changing invalidation, or safely share their verification result, so legitimate concurrent reads both receive the current verified token. Preserve the existing regression proving that a later missing-session observation invalidates earlier pending validation, and continue invalidating on logout/new identity/provider rejection. Add a positive concurrent-read regression alongside that negative race test.
- **Evidence:** [probe source](spec-review-token-concurrency-probe.cjs), [actual probe output](spec-review-token-concurrency-probe.json). Command: `node .superpowers/sdd/2026-10-19-upgrade-auth-session-integration/spec-review-token-concurrency-probe.cjs`; exit 0, `concurrentResults: [null, "synthetic-access"]`.

## Confirmed scope and implemented requirements

Independent file/hash comparison found exactly seven changed existing source/test files and ten new source/test/script files, matching the 17-path source freeze. All before snapshots match their baseline hashes; all 17 current source hashes and all seven browser-input hashes match the recorded freeze. All 35 evidence-manifest entries match their current bytes. The 741 baseline paths checked across earlier research evidence, dependency manifests/lockfiles and root migrations are unchanged. Saved `next-env.d.ts` starting bytes also match. Existing invitation tests, signin, AuthProvider, auth-return helpers and callback remain byte-identical to the batch baseline.

- The facade uses the installed browser cookie-backed PKCE client and a browser singleton; URL auto-detection is explicitly disabled. Its only legacy storage operations remove `auth-store`, the exact project SDK session key, and its verifier key. It does not enumerate storage or import cached identity. The preview stub explicitly fails all application-used auth methods, including OTP and setSession. Server-side facade calls produce separate anonymous clients with persistence, auto-refresh and URL detection disabled.
- The store has no persist middleware, subscribes before session resolution, coalesces initialization, and registers one application listener. Listener identity verification is deferred outside the SDK callback. Session shape and matching provider `getUser(access_token)` are required before publishing authenticated identity. The existing negative lifecycle tests cover stale initialization, stale provider results, identity replacement, signout, signup confirmation and newer missing-session observations. The concurrent successful-read case above is missing.
- The request guard uses public credentials for both explicit Bearer and cookie verification. Malformed or rejected explicit Authorization cannot fall back to cookies. Cookie identity is provider-confirmed, with SDK getAll/setAll, unrestricted chunk inventory and serialized options/deletions. The real SDK fixture tests cover more than five chunks, stale `.12` deletion, refresh and deletion responses, forged claims, safe failures, abort and a ten-second stalled-body deadline. Its transport allows one user lookup and at most one refresh, rejects unexpected/repeated requests and HTTP redirects, and avoids raw transport logging.
- OTP validates a complete session/user through the existing shared predicate, uses safe next for navigation and resend, restricts input to six digits, and invalidates results after unmount/context/location changes. Its synchronous busy guard excludes duplicate or overlapping verify/resend operations. Home no longer moves fragment credentials into query; auth-shaped input is cleaned before a fixed signin error. Only the single bare `type=invite` query without fragment or additional query entries uses the existing `router.push` guidance; that branch contains no auth/session/fetch access. Existing invitation assertions are unchanged.
- The obsolete malformed-domain middleware rewrite is removed. Normal locale delegation remains. The original callback and strict signin-return protections are unchanged: selected single exchange, verifier-only callback reads, cookie-preserving 303, fixed errors, deadline, safe next and eight-locale behavior.

## Evidence assessment and boundaries

The focused log records 18 suites / 505 tests passed. It includes existing signin, callback, auth-return, store and invitation regressions; the modified existing store test strengthens success fixtures with complete sessions/provider identity and asserts fixed errors rather than weakening the substantive success/failure checks. Actual RED logs and source snapshots remain, including the old implicit/no-cookie behavior, stale cached identity and OTP false success. Typecheck has its recorded successful command output; scoped lint has an empty successful output corroborated by the implementer's process report. These runs were inspected, not rerun by this reviewer.

The 14-check Chromium script genuinely bundles the production facade/store, invokes production callback/guard behind a local adapter and uses real Chromium cookies/navigation. The fixture validates S256 challenge/verifier correspondence, consumes codes once, issues synthetic tokens and verifies their membership. The captured chain supports OAuth, email PKCE code, token_hash, numeric OTP, browser restoration, cookie/Bearer identity agreement, invalid Bearer refusal, missing-verifier/mixed-input refusal and post-signout SSR refusal. Browser request interception is restricted to the fixture's exact loopback origin, with service workers blocked. Cleanup records no listening fixture or sockets, a closed owned browser and removed owned temp directory. Two recorded 401 console messages belong to deliberate negative requests.

This is a synthetic local bridge, not a full Next-rendered application. React OTP/home/signin behavior and normal locale delegation are assessed through their separate component/unit tests, not by the Chromium bridge. Refresh/chunk/deadline and additional invalid-input cases are covered by actual-SDK focused tests rather than all being repeated in Chromium. The two findings expose acceptance cases absent from the passing evidence. This review ran only the two tightly scoped synthetic probes, changed no application source, used no remote services, and ran no broad suites. Controller-owned full project verify/shared/infra checks remain pending. Live Google, SMTP, JWT signatures, RLS/PostgREST, production domains/deployment and real-device qualification remain unproven; their existing blockers alone are not findings against this local batch.
