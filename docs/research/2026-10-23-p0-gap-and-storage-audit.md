## 正式 adapter 的执行顺序

1. 本批已完成精确定义采集/静态审查和旧删除拒绝。下一项按[语义审查](evidence/2026-10-23-storage-definition-capture/semantic-audit.md)将完整enum与已审触发器加入隔离PG17兼容演练，分开归因删除GUC、角色、RLS和对象更新时间；旧快照之外的角色图/服务设置保持未验证。
2. 形成七个未登记迁移的逐项语义对账；将审查结果落实到正式资产/Storage/删除adapter的事务与迁移规格。只在隔离环境制定新增结构、权限与兼容迁移，不重放 bootstrap 或运行 repair。
3. 经最小字段范围核准后，盘点 bucket/key/字节/MIME/版本或更新时间/校验值/来源引用；不得扫描家庭正文。缺件、同名、冲突、无法确认归属分别保留，不能自动映射。
4. 正式资产事务消费受信来源快照和对象核查：在一个提交边界重查项目动作、用途、墓碑、来源版本及对象版本；失败返回未确认，不能产生ready/清理本地块。已有实验账本需要正式schema/RLS/HTTP接入。
5. 在隔离 Supabase 环境，用两虚构家庭验证私有桶/签名/直接SDK/撤权/旧URL/跨家庭读写；本地PG的 claim shim 不能替代真正 JWT/PostgREST/Storage HTTP。当前没有隔离项目，需确定环境与预算后才能完成这项。
6. 删除请求事务先撤销新访问/处理并登记墓碑、原件/派生件/引用目标及幂等请求；Worker只经 Storage API 删除对象，逐件确认缺失/错误/未知结果；保留不可变键防止重试删到新对象。数据库/存储分布式操作不假装单事务，未知结果先查询再重试。恢复后先重放墓碑再开放访问。
7. 接入录音封口、任务发布与完整导出，并执行 G1。重新开启旧入口不是回退方案；回退停新写入/处理、保留数据与拒绝规则。

## 无托管备份时的恢复方案

用户已确认 Free Backups 未开启、音视频无独立副本、没有隔离 Supabase 项目；图片副本未知。这些信息无需重问。当前 metadata_reader 仅用于目录读取，不能拿它导出业务表或媒体。

拟采用“数据库逻辑备份＋媒体独立副本＋单独保存的删除墓碑/清单”，待负责人确定受控存储位置、容量/预算与隔离恢复目标后执行。此方案没有购买套餐或备份成功声明，也不承诺当前可达到7/30天删除期限。

- 备份须覆盖应用schema/数据、角色与授权的可重建定义、Auth依赖及实际Storage对象；仅数据库dump不包含音视频字节。外部邮件/支付/AI配置列为独立恢复依赖，秘密留在受控secret存储，不放报告。
- 取得一个冻结点（维护期停写，或有经验证的版本快照方案），分别保存对象计数、字节、SHA-256和精确bucket/key与引用清单。若尚无可证明的一致性切点，记录不一致并保留旧副本，不能称完整备份。
- 先用虚构两家庭、音频/图片/派生件与待删目标做隔离恢复。验证数据引用、所有对象校验、跨家庭拒绝、新短链/公开路径边界，先重放冻结点之后的墓碑，再进行可读性与导出核验。
- 对照冻结清单报告缺件、额外对象、哈希不符和未恢复依赖；恢复合格后才据此写正式回退步骤。保留原件，不以“复制完成”或“dump退出0”替代恢复结果。
- 确认副本加密/访问权、定期检查、保留期限和删除传播；普通版本控制或生命周期设置不等于备份，当前两桶versioning为DISABLED。
