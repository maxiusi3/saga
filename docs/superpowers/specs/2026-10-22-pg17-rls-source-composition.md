# PG17 RLS 与来源账本组合验证

2026-10-22（Asia/Taipei）。落实 handoff 的下一本地实施项。用户继续授权按升级计划推进；真机验证先跳过，需要用户协作的事项另列步骤。跳过不等于质量门通过。

## 目标与边界

在已有固定 PostgreSQL 17.4、Node 和 pg 运行时中执行旧 RLS 与来源账本的行为矩阵，并把已审查的公共函数、表结构、触发器和邀请/权益修复组合到同一临时数据库，发现原来的缩减夹具掩盖的兼容问题。只新增 `experiments/pg17-rls-source-composition/` 与本批证据、文档。前批实验、业务代码、依赖、根迁移和原始证据保持不变。

“完整依赖”指已取得且已审查的本地关系/公共函数依赖组合，不表示复制完整 Supabase。固定元数据中未取得函数体的 Storage 触发器、完整 enum 定义、真实 Auth/JWT/PostgREST、Storage HTTP 和生产角色继承不得猜测为已验证；明确列出未重放项。只用虚构家庭、来源与对象。不开启生产功能，不连接远端，不提交/推送/迁移/部署，除非原 P0/里程碑条件实证通过。

## 组合与可核查差异

1. 复用 `pg17-routines` 的 Harness、固定 capture 与 replay，保留七张公共表的完整结构、13 个已审查函数定义及三处公共更新时间触发器。新增完整 `public.stories` 元数据结构、约束/索引和已审查的第四处同一更新时间触发器。加入来源账本所需、明确标为 synthetic 的 project/story tombstone 与 t02 表，不改旧 ledger adapter。
2. Storage 至少覆盖旧 RLS 依赖的全部列、真实空值、owner 两种字段、bucket FK、生成 path_tokens 和固定快照内对象唯一索引。能物化的 buckets/objects 结构与约束按固定快照建立；必要本地 shim、未取得的 enum/Storage trigger 语义逐项写入 manifest。不可通过添加旧版唯一约束遮盖实际 upsert 索引变化。
3. 重放旧 32 条策略的完整关系图；先记录原状及原诊断的区别，再应用既有 RLS candidate。允许只改本地数据库名保护条件的派生应用，需固定原文件哈希、检查精确替换次数并记录派生哈希，权限逻辑不得静默改写。使用真实 anon/authenticated 低权限连接，保留全部表的 RLS 和对意外宽松策略的防护。
4. 复用旧 `rls-rehearsal/scenarios.mjs` 的全部候选场景和旧 `t02-source-ledger/scenarios.cjs` 的完整 run。旧缩减夹具中的位置 INSERT 在新测试适配层改为明确列名；只对白名单中的精确语句改写并记载。旧行恢复校验因真实 updated_at trigger 而变化时，只排除该时间戳，另独立验证 trigger 确实运行及所有业务/来源列保持原值。真实 Storage 部分唯一索引需要的 ON CONFLICT 条件明确反映在测试 SQL；不把 42P10 当权限拒绝。新增适配必须先有暴露旧假设的 RED 或直接数据库失败证据。
5. 来源账本实际 TypeScript projector、ledger 操作、追加历史、source removal、SQL NULL/JSON null、数组下界/顺序/类型、并发锁链、撤权、墓碑、回滚与 COMMIT 回执丢失恢复都在 PG17 运行。跨 PG14/PG17 摘要字符串不宣称普遍稳定；记录可重复的本批表示案例及明确适用版本。
6. 组合已冻结 entitlement/invitation/management candidates，至少证明：可信事件授予→邀请接受→当前角色可读本项目 story/object；跨家庭拒绝；来源撤销引起成员停用→下一语句 story/object 拒绝；来源账本绑定在撤权后拒绝。七个旧写 RPC 及钱包/成员写入旁路继续拒绝。不同旧矩阵需要不同 seed 时使用清楚的阶段或重新建立隔离数据库，最终组合用自己的端到端 seed，不能声称分开执行等同组合验证。
