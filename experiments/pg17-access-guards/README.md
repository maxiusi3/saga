# PostgreSQL 17 access-guard rehearsal

This isolated experiment applies two local candidates to the exact reviewed 12 RPC definitions and timestamp trigger replayed by the previous PG17 harness. It implements the [binding access-guards spec](../../docs/superpowers/specs/2026-10-18-rpc-access-guards.md). All data is synthetic. It does not contact Supabase, use real authentication/email/payment services, deploy a migration, or alter prior experiments.

Run from the repository root with the existing pinned Node and PostgreSQL installation:

```sh
node experiments/pg17-access-guards/verify.mjs --red
node experiments/pg17-access-guards/verify.mjs
node experiments/pg17-access-guards/verify-lifecycle.mjs
```

`--red` deliberately exits 1. It checks the original routines before any candidate is applied: missing and forged authenticated identities must be rejected, and zero vouchers must create no project or role. The first persisted RED was executed before `candidate.sql` existed. Each run writes a unique immutable JSON evidence file under `docs/research/evidence/2026-10-18-rpc-access-guards/`; it never overwrites earlier evidence. `--test-signal-ready`, `--test-fail-start`, and `--test-client-failure` are bounded observer-only failure paths. The lifecycle observer also runs the complete suite with hostile `PG*` / `DATABASE_URL` values, and checks exit status, empty stderr, safe stdout, absent postmaster PID and removed scratch directory. No rescue cleanup is acceptable for a passing lifecycle case.

`candidate.sql` requires database `saga_pg17_rehearsal` and its own session marker `saga.pg17_access_guards='only_synthetic_local'` inside a DDL transaction. The prior export marker alone is insufficient. Original parameter names, the sole `creator_role DEFAULT 'facilitator'` default, TABLE/UUID results, volatility and non-strict semantics are checked against the actual replayed catalog. Both routines retain the private fixture owner, use empty search paths with qualified objects, revoke PUBLIC/anon/metadata_reader/service_role EXECUTE, and grant authenticated EXECUTE. The synthetic table ACL denies direct writes and the four caller roles cannot escalate; that is a local test boundary, not a reproduction of all production ACL/RLS or role inheritance.

Acceptance takes a **project lock followed by the target member lock**. The initial member read stores `(project_id,user_id)` as the call's binding-consistency reference and locates the project. After waiting, the locked tuple must equal that reference using NULL-safe comparisons; authorization separately checks the current authenticated user, pending state, legal role, active project and current facilitator/inviter relationship. A changed user binding is rejected for either the former user or the invoking replacement user when the locked tuple differs from the first observed tuple. Success only activates that row and returns its stored timestamp; it creates no member and spends no resource. Repeat acceptance explicitly fails without changing `joined_at`. The existing `project_roles.id` entry point is not an email token adapter. Missing/stale inviters fail without repairing history. A valid committed binding before the first lookup is judged as current fact. The existing signature/schema cannot prove lifetime binding immutability or detect a change and restoration to the same tuple between reads (ABA). Token/email verification, expiry and trusted persistent seat reservation remain future integration work described in the [invitation audit](../../docs/research/2026-10-18-invitation-compatibility.md).

The focused `accept_committed_valid_rebinding_has_no_prior_version_fact` case first changes both user and project in a committed fixture transaction, keeping the current inviter valid, then calls as the newly bound user. It succeeds using the current binding, consistent with the clarified spec's first-lookup boundary. The separate `concurrent_rebind_to_invoking_new_user_after_locator_denied` case retains the prior committed user while a changer holds an uncommitted replacement, observes the replacement user's acceptance waiting on that changer, then verifies `42501` and zero accepting-call writes across all seven tables after the changer commits. Its first run against the pre-fix candidate genuinely failed and is preserved separately. Neither case claims historical immutability.

Creation locks the existing caller wallet before checking resources, consumes one voucher and one seat matching either supported role, then inserts the caller-owned active project, active creator member and two matching `consume` records in one transaction. Missing/NULL/insufficient relevant balances fail; the other role balance and payment reference stay unchanged. NULL or ordinary whitespace-only names and explicit NULL/invalid roles fail; empty description becomes NULL. The project explicitly uses `payment_status='unverified'`, because a legacy wallet balance or consumption record is not proof of payment. The fixture column's default `paid` is intentionally overridden.

The suite compares complete snapshots of projects, project_roles, wallets, seat_transactions, project_members, export_requests and notifications around every denial and injected failure. Public reports contain only counts and hashes for those snapshots. Real CHECK failures cover wallet updates, project/member insertion and both consumption resources. Explicit caller rollback, DDL rollback, repeat DDL application and preserved historical rows are separate cases. A malformed legacy role test temporarily removes and restores the role CHECK solely in its synthetic fixture.

Concurrency uses separate real database connections and explicit transactions. It observes ungranted `pg_locks`, wait events and `pg_blocking_pids`, and records the holder's granted locks. The cases cover two accepts; revoke, member delete, user/project rebinding, inviter change, project transfer/deactivation/deletion in both orders; and both role resources under voucher scarcity, seat scarcity, two complete allocations and rollback of the first creator. Observer snapshots confirm uncommitted intermediate writes remain invisible. Waits have bounded statement/lock/deadline limits. The suite then composes with the prior export candidate: unauthorized acceptance cannot manufacture export access, legitimate acceptance registers a durable request through either export overload, and revocation rejects further requests while retaining history.

There is no request idempotency key. Two funded requests may each create a distinct project and consume separate resources. A lost response after acceptance requires reading the current bound member; it must not automatically recreate an invitation. A creation timeout or disconnected response has an unknown commit outcome and cannot safely be retried as though no write occurred. This rehearsal proves database transaction rollback for observed SQL errors and caller rollback; it does not simulate a remote network's unknown commit response or provide retry deduplication.

`input-pins.json` records the finalized source inputs, all loaded CommonJS files and their package manifests, the Node executable, and the entire existing PostgreSQL installed bin/lib/share support tree. Every normal/RED/failure-path runner checks these pins. The replay module separately verifies the fixed public/private capture, all 13 full definition digests and selected schema snapshot. Reports record their input manifest digest, direct ESM/SQL/README support hashes, exact CommonJS closure, runtime binary pins, runtime support verification, actual catalog and end-of-run source stability. The macOS kernel/libSystem shared cache remain ambient platform dependencies and are explicitly disclosed, rather than described as byte-pinned. No private routine body, private package name, raw database error message, detail or context is emitted. The old harness itself supplies the synthetic `auth.uid()` claim shim and UUID shim; neither is real authentication.

Independent review and application/milestone checks belong to the batch controller. Passing this local experiment does not establish trusted wallet grants, safe payment RPCs, real JWT/role inheritance, production RLS/table ACL, Storage security, full invitation compatibility, a release milestone or deployment readiness. There is no destructive down migration; failed candidate DDL rolls back atomically, and repeat application preserves business history.
