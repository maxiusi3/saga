# Local notification authorization rehearsal

This experiment privately replays only the independently audited F05 and F07 definitions from the pinned 2026-10-17 capture. Raw definitions never enter these public files or reports. It invokes no remote routine, network endpoint, application adapter, root migration, or previous experiment.

Run `node experiments/routine-notifications/verify.mjs` from the repository root. `--red` runs the same denial expectations against the captured definitions without applying the candidate; its failure is intentional and recorded. `node experiments/routine-notifications/verify-lifecycle.mjs` checks a hostile PostgreSQL environment, real SIGTERM exit 143, and a real failed server startup. Reports use unique, exclusively created `notification-*.json` names in the routine-audit evidence directory.

PostgreSQL 16 comes from `/usr/local/opt/postgresql@16/bin`; PostgreSQL 17 is unverified. The existing `pg` installation under `experiments/t05-durable-worker/node_modules` is read as a dependency without editing it or adding packages. PG environment variables and DATABASE_URL are erased before loading `pg` and before subprocesses. Clients have an explicit private Unix socket, database, role, port, inert nonempty password, ssl:false and timeouts. TCP listening is disabled. The runner owns one private temporary directory, and removes it only after server stop is confirmed. An unknown stop result preserves the directory and fails the report.

The fixture contains only five referenced notification columns, an `auth.users` key table, and synthetic family labels. Its column types and nullability match the relevant pinned snapshot subset. It omits unrelated columns, indexes, checks, defaults and foreign keys; no extension or noninternal trigger is installed. The captured notification table has no noninternal triggers. A non-login table owner owns the routines and table, so SECURITY DEFINER bypasses non-forced RLS through table ownership. It is not a simulation of every privilege of the remote postgres role.

All four caller roles are separate non-superuser, NOBYPASSRLS direct connections. The synthetic self policies are defense in depth; table privileges are denied to all callers, deliberately stricter than the remote snapshot. Baseline reproduction therefore demonstrates that function execution bypasses an otherwise closed table boundary. The local `auth.uid()` helper accepts a session GUC. It models the claim adapter after trusted PostgREST authentication, not cryptographic JWT validation. A metadata login can spoof that GUC; the candidate must still deny it through actual routine EXECUTE privileges. Direct authenticated database credentials are outside this trust model and must not be exposed to clients.

The hand-authored candidate is self-recipient only. It rejects missing/null or mismatched identity, fixes search_path, retains parameter names, integer returns, NULL default, unread-only updates and timestamp behavior, and grants exact routine execution only to authenticated. No service-role fallback is present. No current application callsite was found by the enclosing audit; old or external client compatibility remains unknown. Notifications contain no family key: the family test means a foreign recipient belonging to another synthetic family stays untouched, not that this adds a family-membership policy. An authenticated user with no family and no notifications can read their own empty inbox.

The candidate's database-name and session-marker checks are local accident guards, not unforgeable authorization. This is not a deployable migration. Production deployment needs a separately reviewed owner/role inheritance/table privilege plan, trusted authentication boundary and compatibility decision. The runner verifies transaction rollback after candidate DDL failure and repeat application, then behavior and ACLs. Its `--red` report is an actual failing assertion, not a fabricated expected-failure label.
